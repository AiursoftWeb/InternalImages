# GitLab CI Collector

Copies job lifecycle metadata through GitLab's REST and GraphQL APIs into ClickHouse for Runner backlog and slow-job dashboards. One replica, no public endpoint, no GitLab database access, logs or artifacts.

Set `GITLAB_URL`, `GITLAB_ACCESS_TOKEN` with `read_api`, and `GITLAB_GROUPS` (comma-separated group paths). Only token-visible projects owned by those groups/subgroups are collected; discovery is refreshed hourly. Set `CLICKHOUSE_URL`, `CLICKHOUSE_USER`, `CLICKHOUSE_PASSWORD`; `CLICKHOUSE_DATABASE` defaults to `GitLabMetrics`, and `GITLAB_SOURCE` identifies the source instance. Keep credentials in deployment secrets. No PostgreSQL configuration, socket mounts or administration privileges are needed.

Run `--init-schema` once with schema-management credentials. Normal operation needs SELECT/INSERT on `api_jobs`, `api_project_sync` and `api_sync_runs`, plus SELECT on `api_jobs_latest`. Grafana needs SELECT on the latest view, its underlying table (view invoker permissions), and synchronization tables. Query `api_jobs_latest`, not the versioned base table. No automatic retention or migration of the previous SQL collector's tables is performed.

Defaults: `SYNC_INTERVAL_SECONDS=60`, `BACKFILL_DAYS=30`, `RECHECK_SECONDS=300`, `API_REQUESTS_PER_SECOND=2`. Projects are discovered with paginated REST calls. GraphQL batches change discovery for ten projects per request, then paginates jobs only in changed and known active pipelines. Child pipelines and both retry states are included. Project progress is recorded in batches only after all pages are written; unchanged projects do not generate checkpoint inserts; replayed observations deduplicate immediately. `--once` synchronizes once and returns nonzero on failure. HTTP 429 respects Retry-After on the next cycle; API errors and partial GraphQL errors do not mark a complete synchronization.

The API provides `queuedAt`, `startedAt` and `finishedAt` directly. The current GitLab GraphQL endpoint returns second-resolution times; this is not the former database's microsecond precision. Jobs without a queue timestamp are retained for tracking future stages but are excluded from Runner backlog. Each retry has a distinct job ID. Include cross-window jobs and cap unfinished intervals at the last fully synchronized boundary. Unknown/stale coverage is not zero backlog.

Backfill discovers pipelines updated within the configured history window, not deleted jobs or unlimited historical revisions. New projects get their own backfill progress. Known active pipelines are refreshed even when old; a first-time backfill cannot discover an unchanged pipeline older than its history window. API visibility and group coverage are explicit in `api_sync_runs`; neither empty top-level admin job results nor created jobs are treated as a global Runner queue. Health requires a recent complete cycle covering every discovered project, not merely a successful partial project/page.
